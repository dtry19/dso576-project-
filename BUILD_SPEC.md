# BUILD_SPEC.md — Appliance Listing Review

Build an interactive dashboard that helps Amazon Appliances category managers identify listings that may need clearer or more complete information. Follow three steps: identify recurring concerns in low-rated reviews, compare those concerns with available listing metadata, and prioritize listings for manual investigation.

Use the full cleaned review sample and, when supplied, documented listing metadata as defined in Section 2. Sections 3–5 specify the page, calculations, and technical design; Section 6 defines acceptance checks. Calculate every value from actual inputs rather than illustrative mockup figures. Preserve source files and do not infer unavailable metadata.

## 1. User, decision, and scope

An Amazon Appliances category manager needs to decide which listings deserve investigation for potential information improvements and which attributes may benefit from standardization. The dashboard connects customer feedback with available features, descriptions, and details. It supports investigation rather than automatic edits to listings.

| Workflow | User examines | Dashboard shows | Decision supported |
| --- | --- | --- | --- |
| Identify customer concerns | Rating, review date, verified-purchase status, and product type when available | Concern counts, low-rated review share, and supporting quotations | Which topics recur in the selected reviews |
| Examine metadata gaps | A concern or parent product | Attribute coverage and review evidence beside listing information | Which attributes may be absent, unclear, or require manual comparison |
| Prioritize listings | A ranked parent-product table and selected-product evidence | Transparent investigation priority, supporting review counts, and potential-gap attributes | Which listings to investigate first and what information to check |

The unit of product-level analysis is `parent_asin`, which groups related variants. Parent-level signals do not establish that every variant has the same issue. The dashboard does not establish product defects, prove historical listing omissions, or support sales or inventory decisions. Findings describe the supplied sample rather than the full Amazon Appliances category.

Support two input states using the same page layout:

- **Review-only fallback:** the full cleaned reviews are available but listing metadata is not supplied. Show review analysis, identify products by parent ASIN, omit Product Type, and display unavailable states for metadata comparisons. All products have “Not assessable” investigation priority; no missing-attribute claims are made.
- **Metadata-enabled workflow:** a documented metadata file has been supplied and validated. Enable available listing fields, metadata comparisons, conditional Product Type filtering, and the priority rules in Section 4. Unmatched products remain visible and have “Not assessable” priority.

A successful review-only build does not establish that the metadata-enabled workflow has been completed or validated.

### Row fields

| Column | Definition |
| --- | --- |
| `rating` | Customer star rating. Values in the inspected files are whole numbers from 1 through 5. A low-rated review means a rating of 1 or 2 stars. |
| `title` | Customer-written **review title**; it is not a product or listing title. |
| `text` | Customer-written review body and the main source for identifying recurring concerns. |
| `images` | List of images attached to the review. An empty list means that the review has no attached image. |
| `asin` | Amazon identifier for the reviewed item or variant; suitable for item-level grouping. |
| `parent_asin` | Parent product identifier used to group related item variants. |
| `user_id` | Identifier for the reviewer. Treat it as an opaque identifier, not customer profile information. |
| `timestamp` | Review time: epoch milliseconds in the original sample and an ISO-style date-time string in the cleaned files. Parse it as a date-time before filtering by review date. |
| `helpful_vote` | Nonnegative count of helpful votes recorded for the review. |
| `verified_purchase` | Boolean indicating whether the review is marked as a verified purchase. |
| `original_row_number` | One-based source row number added to cleaned files for traceability. It is not present in the original sample and is not a permanent review ID. |

The current files contain review data and product identifiers, but **do not contain product name, product type, features, description, dimensions, details, or other listing-metadata fields** shown in the mockup. Therefore, metadata coverage, metadata gaps, and product-type filters cannot be calculated from the current project files alone. Do not infer those fields from review text or mistake `title` for a product name. ASIN-level review metrics can still be calculated, but any listing-metadata feature requires a separately supplied and documented product metadata file.

### Listing metadata input contract

The builder must accept this documented path explicitly; it must not guess a filename or fetch metadata at runtime.

Normalize metadata to one record per `parent_asin`, with these mapped fields:

| Normalized field | Contract |
| --- | --- |
| `parent_asin` | Required non-empty join key, unique after documented normalization. |
| `product_title` | Listing title, distinct from the customer review's `title`. |
| `product_type` | Optional source-provided product category/type; never inferred from reviews. |
| `features` | Listing feature text or a list of feature strings. |
| `description` | Listing description text or a list of description strings. |
| `details` | Structured listing attributes, preserving keys, values, and units. |

Document source-field mappings for title, features, description, and details even when a field is unavailable. Preserve the distinction between an unavailable source field, a null/empty field in an available source, and a failed attribute match in searchable content. Unavailable source fields cannot establish an information gap. If the fields needed for a concern comparison are unavailable, label that comparison “Manual review needed” rather than assume absence.

Reject invalid keys, incompatible field types, and unresolved duplicate parent records. If metadata is organized by variant, document the variant mapping and resolve conflicts before joining; do not combine contradictory values arbitrarily. Left-join reviews to metadata with a many-to-one constraint so no reviews are lost or duplicated. Report match coverage by distinct reviewed parent ASINs. Retain metadata provenance and source excerpts for investigation.

Metadata is optional for the review-only fallback and required for the metadata-enabled workflow. ### Validation and verification

When loading a JSONL file, report an actionable error that names the file, line number, and field. Do not silently repair or discard invalid records. Check that:

- every nonblank line is valid JSON and contains the expected columns;
- `rating` is numeric, whole, and between 1 and 5;
- `title` and `text` are strings, `images` is a list, and `verified_purchase` is boolean;
- `asin`, `parent_asin`, and `user_id` are non-empty strings;
- `timestamp` is numeric epoch milliseconds in the raw file or a parseable date-time in a cleaned file;
- `helpful_vote` is a nonnegative whole number;
- cleaned `original_row_number` values are whole, unique, in source range, and map back to the corresponding raw records;
- the full cleaned file has the same row count as the source, and, when the QA subset is supplied, every example row matches its full-cleaned record by `original_row_number`; and
- exact duplicate records are flagged for review rather than automatically removed solely because an ASIN or user appears more than once.

The existing specification records the following prior inspection facts; recheck them against the supplied files before reporting validation results. In that inspection, all three review files parsed without malformed JSON or missing/null fields. The full sample contains **1,000 reviews**, **870 distinct `asin` values**, **829 distinct `parent_asin` values**, and **625 distinct users**. It includes **105 low-rated reviews (10.5%)**, **898 verified-purchase reviews**, and review timestamps from September 2009 through March 2023. These are checks against the current files, not values to hard-code in dashboard HTML; displayed metrics must be calculated from the selected input and active filters. Empty image lists are valid and common (957 of 1,000 source rows).

## 3. Page and interaction specification

Use the title **“Appliance Listing Review”**, the subtitle and visual design in Section 5, and three numbered panels matching the decision workflow. Show the actual sample scope and metadata availability prominently. Mockup counts, product names, images, and percentages are illustrative and must be replaced with calculated values or unavailable states.

### Filters and selection

Global filters are **Rating** (all, 1–2 stars, or an individual rating), **Review date** (all dates or years present in the full input), **Verified purchase** (all, verified, or not verified), and **Product Type** only when metadata provides usable type values. Derive options from the loaded inputs and retain options when the current combination returns no reviews. Include an “Unknown / unavailable” type option for unmatched or untyped products. Do not infer types from review text.

Provide a searchable parent-ASIN selection control and selectable table rows. This is an evidence selection, not a global filter: it highlights a product and updates its comparison/detail evidence while leaving global cards, charts, and the broader ranking unchanged. Show the source-provided product title when available, always alongside its parent ASIN. Otherwise show the parent ASIN alone.

Concern selection highlights the relevant metadata attributes and narrows supporting evidence without changing global cards, concern denominators, or priority calculations. Product and concern selections can be cleared independently. Reset clears all filters and selections. All controls need persistent labels, keyboard operation, and visible focus.

### Summary cards and denominators

Show four cards for the globally filtered review scope:

1. **Reviews:** number of review rows.
2. **Low-rated reviews:** count and percentage with rating 1 or 2, divided by all filtered reviews.
3. **Reviewed parent ASINs:** distinct parent identifiers in those reviews, not all products in the metadata file.
4. **Metadata match coverage:** distinct reviewed parents with a matching metadata record divided by all distinct reviewed parents, with numerator and denominator visible. Without a supplied metadata file, display “Not supplied,” not 0%. With supplied metadata but no matches, show 0% when the denominator is positive.

For an empty review scope, show zero counts and N/A percentages; without metadata, the fourth card continues to say “Not supplied.” Verified-purchase statistics may appear in selected-product evidence but are not a fifth required summary card.

### 1 — Identify customer concerns

Show a ranked horizontal bar chart for the concern categories defined in Section 4, a low-rated review-share chart, and expandable supporting review evidence. Count each review once per concern; use all filtered low-rated reviews as the concern-percentage denominator. A review may support several categories. Keep unmatched low-rated reviews in the denominator and explain that category shares can overlap.

The low-rated share chart groups ratings into 1–2, 3, and 4–5 stars, with all filtered reviews as its denominator. Retain zero categories. If no low-rated reviews remain, explain that no concern evidence is available under the active filters. A monthly activity chart is optional, not a required replacement for a workflow panel.

### 2 — Examine metadata gaps

When metadata is available, show non-empty field coverage for listing title, features, description, and details across distinct matched reviewed parents. Label denominators and source-field availability; omit a numerical bar for a field absent from the source schema. Show N/A when no matched products remain. Field coverage measures populated fields, not whether a particular attribute is adequately explained.

Add a concern-to-attribute table and side-by-side customer review and listing excerpts for the selected parent and concern. Show supporting review counts and assessment statuses rather than an undefined percentage “gap” score. Apply Section 4's rules to distinguish potential information gaps, available evidence, and manual-review cases. With no supplied metadata show “Listing metadata not supplied”; for an unmatched selected parent show “No matching metadata record.” Neither state implies a missing listing attribute.

### 3 — Prioritize listings for investigation

Show one table row per parent ASIN in the global review scope, including product title and type when available, parent ASIN, total reviews, low-rated count/share, distinct reviews supporting potential gaps, potential-gap attributes, and investigation priority. Use the priority and sorting rules in Section 4 for metadata-enabled analysis.

In review-only mode, show “Not assessable” for every priority and N/A for gap metrics. Sort by low-rated review count descending, total review count descending, then parent ASIN ascending. This fallback order shows where review evidence exists without claiming metadata-based priority. With supplied metadata, unmatched products also use N/A gap metrics and “Not assessable”; matched, assessable products with no gap signal may show a zero supporting count.

The selected-product panel shows total reviews, low-rated count/share, average rating, and verified-purchase count/share from that parent's globally filtered reviews. Include actual review rating, title, body, date, helpful votes, verified-purchase status, and item ASIN. Show source listing excerpts and a proposed manual check only when supporting metadata exists. Truncate long text visually with accessible expand/collapse controls and preserve source text. Do not display reviewer identifiers.

### Empty states and limitations

If global filters return no reviews, retain headings and controls, show zero/N/A cards as specified, and display “No reviews match these filters” in charts and the ranking table. If a retained product selection has no reviews under the current filters, keep its selection and clear control, show an empty evidence message, and do not display stale review metrics. Clearing a selection does not change global filters or summary metrics.

The footer identifies actual sources, sample size, date range, and metadata availability. Concern matches and potential gaps are screening signals for manual investigation, not proof of defects, incorrect listing information, or what the customer saw at the time of purchase.

## 4. Components and contracts

The components must support the three-step workflow: identify customer concerns, examine potential metadata gaps, and prioritize listings for investigation. Keep reusable calculations in `appliance_analysis.py` and HTML generation in `build_dashboard.py`. Functions must return structured values or DataFrames rather than only print results.

| Component | Input | Output | Correctness check |
| --- | --- | --- | --- |
| `load_reviews` | Full cleaned review JSONL and raw source for reconciliation | Validated reviews with parsed dates and source-row identifiers | Enforces Section 2 validation and preserves one row per source review. |
| `load_metadata` | Separately supplied listing metadata and a documented field mapping | One normalized metadata record per `parent_asin`, retaining original fields and source information | Rejects blank keys and unresolved duplicate keys; records absent fields without inventing values. |
| `join_reviews_metadata` | Validated reviews and metadata | Reviews linked to metadata, with an explicit match status | Uses a many-to-one left join on `parent_asin`; review count and review identifiers remain unchanged. Reports unmatched identifiers. |
| `tag_concerns` | Review titles/bodies and documented concern rules | Review-to-concern matches with supporting text | Uses only 1–2-star reviews; counts each review at most once per concern and retains evidence for each match. |
| `assess_metadata` | Relevant parent identifiers, matched metadata, and concern-to-attribute rules | Field coverage and a parent-by-concern evidence table | Distinguishes missing records, empty fields, missing attribute evidence, available evidence, and cases requiring manual comparison. |
| `summarize_scope` | Linked reviews, concern matches, metadata assessments, and active filters | Summary cards, chart series, and concern/coverage comparisons | All review metrics use one filtered review set; product metrics count distinct parent identifiers rather than joined review rows. |
| `rank_listings` | Filtered review evidence and metadata assessments | One row per parent ASIN with supporting counts, potential gaps, and investigation priority | Ranking follows the explicit rule below, with deterministic ties and visible sample sizes. |
| `get_listing_evidence` | Selected parent ASIN and current filtered scope | Supporting reviews, listing field excerpts, and potential follow-up checks | Every quotation and metadata excerpt is traceable to its source; review titles are never used as product names. |
| `build_dashboard.py` | Validated analysis outputs and source text needed for interaction | Self-contained `dashboard.html` | Offline controls update all components consistently, and displayed values reconcile to reusable calculations. |

### Metadata prerequisite and comparison rules

The metadata-enabled workflow requires an additional, documented metadata file; the review-only fallback does not. Use the input contract and source-field availability rules in Section 2 for `parent_asin`, product title, optional product type, features, description, and details. Record the source and extraction date where known. Retain structured attribute keys and units. Do not treat review data's `title` as a listing title or infer product type from customer comments. If metadata is supplied at variant level, define the variant mapping before joining; do not arbitrarily collapse conflicting variants into a parent record.

Until this input is supplied, show review analysis and label the metadata panels **“Listing metadata not supplied.”** Do not classify unmatched products as having missing listing attributes. Unmatched records after a valid metadata load use **“No matching metadata record.”**

Define an inspectable concern dictionary for installation, size/dimensions, compatibility, noise, missing parts, instructions, and durability. Document keywords, phrase matching, normalization, exclusions, and the relevant metadata attributes for each concern. Matches are screening signals, not verified complaints: a phrase may be negated, ambiguous, or unrelated to an information gap. Allow a review to match several concerns and explain that concern percentages therefore need not sum to 100%.

For each concern, report its distinct supporting review count and share of all filtered low-rated reviews, including low-rated reviews with no matched concern in the denominator. For field coverage of a source-provided field, divide the number of distinct matched parent ASINs with a non-empty field by the number of distinct matched parent ASINs in the filtered scope. For a field absent from the source schema, show “Source field unavailable” instead of a numerical coverage value. With zero matched parents, coverage is N/A. Display that denominator and metadata match coverage separately. A non-empty description does not establish that dimensions or compatibility information is present.

At the parent-and-concern level, flag a **potential information gap** only when a metadata record is available, all fields required by the documented concern rule are available in the source schema, and the rule finds no relevant evidence in those fields. An empty value in an available field can support a potential gap; an unavailable source field cannot. Preserve the fields searched and matching excerpts. An available attribute is not proof that the listing is correct or clear. Label unresolvable comparisons **“Manual review needed.”** Claim a potential inconsistency only when explicit, comparable values and units support it; otherwise show the review and listing text side by side. Metadata may reflect a different time from the review, so do not claim it represents what the customer originally saw.

### Investigation priority

For an initial, transparent screening rule, count distinct filtered low-rated reviews mentioning at least one concern with a potential information gap for that parent ASIN. Count a review once even when it supports multiple gaps. Assign **High** for 3 or more such reviews, **Medium** for 2, and **Low** for 1. Products with no such evidence show **“No gap signal under these rules”**; unavailable or unmatched metadata shows **“Not assessable.”** A product with no supported gap signal but at least one concern that cannot be assessed because required source fields are unavailable also shows **“Not assessable”**, rather than “No gap signal.” If a supported gap gives a High, Medium, or Low priority despite other unassessable concerns, retain that priority and disclose the incomplete assessment. Gap metrics are N/A when no metadata-based assessment is possible. These labels indicate investigation priority, not defect severity or a validated assessment of listing quality.

Sort High, Medium, and Low first, followed by no-gap-signal and not-assessable records. Within each group, sort by supporting review count descending, distinct potential-gap attributes descending, and `parent_asin` ascending, placing N/A metrics last. Display total reviews and low-rated reviews alongside the supporting count. Document these initial thresholds and expose the evidence behind each label. In review-only mode, use the fallback ordering in Section 3; do not apply metadata-based ranking.
